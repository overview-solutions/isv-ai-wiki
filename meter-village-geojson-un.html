Village map packs · open Utility Network GeoJSON

Esri Utility Network semantics in open files · no ArcGIS lock-in · starter for ~100–1000 meter LV villages

IEEE Smart Village Technology Committee uses a GeoJSON + JSON pack so a mini-grid can be loaded offline into the Village Simulator, traced by feeder, and later bound to read-only metering application programming interfaces (APIs). Ideas borrow from Esri’s Utility Network (devices, junctions, lines, subnetworks, associations) without requiring Esri software.

Source of truth (code)

Living schema + demo pack: smart-village-simulator/villages ↗ (_schema/, _template/, demo-lv/). This page is the human map of that contract.

Why this shape

Geometry stays in files. Telemetry stays on demand by asset id. A thousand-meter village must not dump a year of kWh into GeoJSON. Map packs travel offline (USB, laptop, no cloud). When an asset is selected, a feed registry resolves that id to a read-only API or message topic.

Essential vs nice-to-have layers

How this split was defined: a Technology Committee Map Twin minimum — what you need to open a village offline in the Village Simulator, pick a feeder, and reach meters by stable id. Sized for ~100–1000 customer meters. Contract lives in smart-village-simulator/villages/_schema.

Sample layers: the simulator ships villages/demo-lv/ with at least one feature in every Essential file and every Nice-to-have class listed below (junctions, enclosure, disconnect, recloser, neutral, terminals, containment / attachment, and feeds/registry.json). Copy that pack or start from villages/_template/.

Sized for a schematic village on the order of 100–1000 customer meters (one island, a few feeders). Scale by repeating feeders and service laterals — do not invent a transmission model.

Essential — Map Twin minimum

  • village.json — site id, name, WGS84 origin, bbox, status
  • network/subnetworks.geojson — island + each feeder
  • network/structure.geojson — poles (cabinets optional here)
  • network/electric-lines.geojson — trunk / primary / secondary / service
  • network/electric-devices.geojson — meters, transformers, generation or station head, EMS cabinets if used
  • network/associations.json — connectivity edges joining those ids
  • Every feature: stable id, assetClass, assetGroup, subnetworkId

Nice-to-have — fuller UN completeness

  • network/electric-junctions.geojson — bus, splice, tap, service_point (Esri Junction class)
  • Structure detail — pad, enclosure, cabinet; later StructureLine / boundary
  • Protection detail — fuse, breaker, disconnect, recloser as separate devices
  • Storage / inverter / DTM as explicit devices beyond gen+station
  • Separate neutral line class; multi-port terminals[] on transformers and EMS
  • phase, nominalKv, ratedA, globalId (UUID)
  • Containment / attachment associations (meter in cabinet, xfmr on pole)
  • feeds/registry.json — Live Twin API bindings by asset id (not required for a pure Map Twin)
Alignment with Esri Utility Network

The essential / nice-to-have split above is not an Esri label — Esri’s Utility Network does not publish that binary list. We borrow semantics, not ArcGIS files. Esri domain networks use Device, Line, Junction, Assembly, and SubnetLine classes, plus a Structure network and associations (connectivity, containment, attachment). See Esri’s domain networks ↗ and structure network ↗.

Maps cleanly: our electric-devices ≈ Device (+ some Assembly roles); electric-lines ≈ Line; structure ≈ StructureJunction; subnetworks ≈ subnetwork / feeder identity (Esri also generates SubnetLine); associations.json ≈ association table.

Deferred to nice-to-have for field practicality: a full Esri build expects Junction features wherever lines meet, Assembly containers, StructureLine / StructureBoundary, terminals on multi-port devices, and systematic containment / attachment. We allow those as richer packs so brownfield teams can ship a traceable meter map before digitizing every splice and vault.

island (subnetwork) └─ station / gen head └─ trunk → feeder heads └─ feeder (subnetworkId) ├─ poles + primary / secondary lines ├─ xfmr → EMS (optional) → service laterals └─ meter ←── same id used later for read-only API

How assets join

associations.json holds the graph. Geometry does not imply connectivity by itself.

  • connectivity — electrical path fromId → toId (optional terminals, phase, subnetworkId)
  • containment — device inside structure (meter in cabinet)
  • attachment — device on structure (transformer on pole)

Trace: walk connectivity within one subnetworkId, then climb toward the island controller. See _schema/connectivity-rules.json in the simulator repo.

Live Twin — metering API binding

feeds/registry.json maps asset id → feed descriptor (URL template, topic, auth ref). Secrets stay out of the pack. Any metering vendor API is welcome; Technology Committee adapters grow over time (including SparkNet-HTTP, GroundBolt-class site stacks, MeshEMS message topics, and others).

Hypothetical vs as-built

village.json status: hypothetical · survey · as-built · unverified. Mock villages built in simulator BUILD mode and real field maps should live in separate stores until a review migrates a pack.
