TC 2.0 technical report

Technical report on the open EarthSpark / SparkMeter stack (ThunderCloud 2.0 / GroundBolt): field meters and CIUs (Customer Interface Units) on a 2.4 GHz mesh, a USB Gateway as the RF bridge, SparkNet-HTTP and Firefly as software plugins (not standalone radios), GroundBolt as the on-site HES (head-end system), optional ThunderCloud (same app in the cloud). Objects below are those this review already named or drew — GroundBolt Postgres / wire objects, village UN GeoJSON packs, and complementary MeshEMS / OpenAMI — not invented tables. Diagrams share one hosting toggle (site-only vs site+cloud).

How ThunderCloud 2.0 (TC2.0) came to be

SparkMeter built prepaid LV (low-voltage) metering for mini-grids and distribution utilities — meters with built-in RF mesh, a site basestation, and cloud software (ThunderCloud / GroundBolt lineage) for billing and control. That stack served a large installed base, but the operator software was historically hard to run outside the vendor’s managed environment: proprietary internals, Chef-era bootstrap, and a soft lock where leaving the SaaS (software-as-a-service) path meant losing a workable head-end system (HES) — the utility software that talks to meters for billing, disconnect, and config.

In September 2025, EarthSpark took over SparkMeter energy-metering operations (on the order of ~1 M people served on the meters). The mandate was continuity for live fleets and an exit from single-vendor software lock where operators could carry the risk. In July 2026 EarthSpark published ThunderCloud 2.0 (also called TC2.0) under Apache-2.0 as an open foundation — same product family as GroundBolt (on-site) and ThunderCloud (cloud), modernized so it can actually be bootstrapped and self-hosted. Hub: sparkmeter.io/open-source · code: github.com/EarthSpark/thundercloud.

Open-sourcing did not cut over the field. Production basestations still run ThunderCloud 1.x (TC1.x) managed SaaS; TC2.0 is explicitly a pre-production foundation, not a drop-in flash for every live site. Community near-term goal (OSEA Discord / GitHub — Open Source Energy Access community around EnAccess): a stable releasable main (Ansible from-scratch converge, SymmetricDS container CI / continuous integration) before years of deferred product features.

Field today vs ideal below Live fleets still run TC1.x managed SaaS. TC2.0 (Jul 2026, Apache-2.0) is a pre-production foundation — not plug-and-play. This page describes the target open architecture operators can commission toward, not a promise that every basestation upgrades overnight.

What problems TC2.0 is aimed at

Vendor soft-lock on the HES (head-end)

Operators could own meters in the field but not realistically run the head-end system themselves. TC2.0 opens GroundBolt / ThunderCloud so self-host (or mix-and-match with managed cloud) is a real path.

Opaque meter↔app contract

meter-driver-spec publishes an HTTP / SSE (Server-Sent Events; optional gRPC) driver contract — energy, power, voltage, enable/disable, tamper, balance flags — so other OEMs (original equipment manufacturers) can aim at the same basestation later.

No clean “talk to meters without the full cloud”

SparkNet-HTTP is the direct meter/gateway path. TC2.0 uses it natively; operators can also use it outside ThunderCloud as a vendor-exit / alternate HES edge.

Site vs cloud were hard to separate

SymmetricDS makes continuous ground↔cloud database sync explicit. Basestation and cloud are not one process — the WAN (wide-area network / internet uplink) can fail while GroundBolt keeps local prepaid and control alive.

Un-reproducible basestation bootstrap

Chef-era installs blocked outsiders. Ansible converge is the TC2.0 bootstrap path so a GroundBolt box can be rebuilt from public tooling.

Asset / key control

Meter crypto keys can stay with EarthSpark, escrow at A2EI (Access to Energy Institute / Access to Energy gGmbH), or move to the operator. That unlocks sovereign ownership — and creates real brick risk if mishandled.

What TC2.0 does not claim to solve alone: CRM (customer relationship management) depth of a mature SaaS, every deferred product feature from a decade of backlog, or Phase 2 ISV (IEEE Smart Village) work (Street-EMS / OpenAMI MQTT telemetry / feeder intelligence). ISV maps TC2.0 under Phase 1 — open operator software for the installed SparkMeter base — complementary to MPM (metering / prepaid management class systems) and to later OpenAMI tracks. See roadmap · ThunderCloud update.

Ideal system state

A village mini-grid powers homes and civic loads over LV feeders. Each prepaid customer has an SM (SparkMeter) meter and a CIU (Customer Interface Unit — keypad / balance display) on a short local link — no cloud required for that UI. Meters join a 2.4 GHz mesh (encrypted / hidden SSID). A USB Gateway bridges that RF to the site computer; GroundBolt speaks to meters through the Gateway. SparkNet-HTTP and Firefly are software plugins on that path (not separate radio boxes).

When the operator wants remote ops, CRM, or multi-site portfolio tools, SymmetricDS syncs the site database to ThunderCloud in the sky (managed EarthSpark SaaS or self-hosted) — same app family as GroundBolt, cloud deploy. Cloud is optional. Commission the field ↔ Gateway ↔ GroundBolt loop first; attach cloud only after that loop is proven.

SM meter / CIU ↔ 2.4 GHz mesh ↔ USB Gateway ↔ SparkNet-HTTP / Firefly (plugins) ↔ GroundBolt   [optional]  ↔ SymmetricDS ↔ ThunderCloud

Managed path

EarthSpark hosts ThunderCloud / supports basestations. Current TC1.x customers stay here. Lowest ops burden; production improvements land here first.

Self-host path

Run GroundBolt on-site and/or ThunderCloud yourself. Mix-and-match (your site + their cloud, or both). Uses the same TC2.0 codebase. Self-host terms still evolving.

What must work before cloud

  • USB Gateway sees meters on the 2.4 GHz mesh; GroundBolt talks through that Gateway.
  • SparkNet-HTTP / Firefly plugins carry commands out and SSE (live event stream) / readings in.
  • GroundBolt shows live kWh, power, voltage, state; can Enable/Disable and push balance (Open Code: read + toggle relays).
  • CIU prepaid UX works locally even if WAN (internet uplink) is down. SM meters do not decode STS / OpenPAYGO tokens — credit is a GroundBolt wallet (set_balance is display). Do not redo STS vending for other meter families here.
  • Meter keys ALWAYS stay on GroundBolt (never move to ThunderCloud even when cloud is enabled) — held by EarthSpark, A2EI escrow, or operator. Mishandling can brick meters.

Layer cheat sheet

L6–L5 · Cloud + sync

ThunderCloud — remote ops / CRM. SymmetricDS — site↔cloud database sync. Optional after site loop works.

L4 · On-site app

GroundBolt — site UI + Postgres at the ops building. Installer hub. Survives WAN outages for local control.

L3 · Driver / plugins

SparkNet-HTTP + Firefly (software plugins) + meter-driver-spec — open contract for commands / SSE / meter capabilities (energy, power, voltage, enable/disable, tamper, …).

L2–L1 · Radio + field

USB Gateway = RF bridge to meter 2.4 GHz mesh; SM meter / CIU at each prepaid home. Gray LV feeders carry power, not data.

GroundBolt as site HES (from this tree)

ThunderCloud and GroundBolt are the same sparkmeter app. On-site: HEROKU unset → GroundBolt. In the cloud: ThunderCloud. Radio is a sibling process. GroundBolt talks HTTP commands out and SSE events in; it never sees SparkNet RF frames inside the USB Gateway.

Source of this section Public TC2.0 developer preview in the thundercloud tree (Aug 2026 pass). README: do not bill real customers. Live fleets still TC1.x managed SaaS. SparkNet RF inside the Gateway is not specified in this repo.

Prepaid loop — pay before watts

POST /api/v0/transaction/ (cash | bonus) → wallet credit → set_balance → CIU → configure_meter enable (if AUTO and credit > 0) → load draws watts → SSE MeterReadingEvent every HEARTBEAT_PERIOD (15 min) → add_reading → CalculateBilling → wallet debit → credit ≤ 0 → configure_meter disable
  • Customer is 1:1 with meter.
  • Payment sources in this tree: cash and bonus only. No mobile-money plugin in-repo.
  • set_balance updates the CIU display. The HES wallet in Postgres is the system of record.
  • meter_config.state = AUTO → relay on iff credit (and plan) > 0.
  • Low-balance SMS fires once per threshold, not every heartbeat.
  • Command queue is in-memory asyncio. Crash drops in-flight jobs; boot reconcile_all() rebuilds the provider roster from Postgres. Hard request→job-ID correlation still under community discussion.

GroundBolt Postgres (system of record)

Readings sync ground→cloud only. SymmetricDS is optional after the site loop works. No Account entity — wallet is meter XOR sales account.

Wire objects (SparkNet-HTTP / plugins)

SSE in — what GroundBolt consumes

meter_reading / meter_reading_phased → add_reading. heartbeat_summary → watchdog log. log → Python logging. Neighbor / network-health / command-lifecycle events exist on the wire; GroundBolt does not persist them.

Commands out

configure_provider (heartbeat 900 s), register_meter, configure_meter (enable/disable, limits), set_balance, unregister_meter. Fire-and-forget via SparkNet-HTTP POST /v1/commands.

On-demand mesh (not stored)

query_meter_neighbors → SSE meter_neighbors (neighbor_id, RSSI, link quality). query_network_health = packet counts + latency, not a path. CLI: meter get-neighborlists.

SparkMAC config, not a route log

sparkmac_node stores forwarding mode (default flooding), optional static_routes, TTL. Site UI “Routing Algorithm” is still an empty TODO. Desired-state pushed to meters — not a hop list per heartbeat.

Village UN GeoJSON pack (geometry, not telemetry)

Separate convention — Esri Utility Network semantics in open files. Same meter id can later bind feeds/registry.json to SparkNet-HTTP / GroundBolt. Geometry stays in files; kWh stays on demand. Full split: Village GeoJSON · UN.

MeshEMS / OpenAMI / MPM — complementary, not TC2.0 tables

MeshEMS (NESL 865B board) and Phase 2 OpenAMI MQTT / Street-EMS are a different track from GroundBolt Postgres. See MeshEMS board · OpenAMI. MPM (MicroPowerManager) owns CRM + other prepaid families (STS, OpenPAYGO). Posting /api/v0/transaction/ from MPM into GroundBolt can share a wallet; two systems of record without a split double-count.

Can you trace mesh routing per meter?

Not from stored readings. NAN is proprietary SparkMAC on 2.4 GHz — not Z-Wave. A legacy emulator can attach hops[] (last_hop, RSSI, retry) to SparkMAC replies; MeterReadingEvent / the reading table drop that. Energy, volts, watts, credit, state only.

On-demand: query_meter_neighbors → SSE meter_neighbors (who this meter hears now: neighbor_id, RSSI, link quality). CLI: meter get-neighborlists. query_network_health is packet counts + latency, not a path. GroundBolt does not write those replies to Postgres. You can poll a neighbor graph if the USB Gateway translator implements the command (contract in this tree; live firmware not in-tree). You cannot replay “this heartbeat went hut A → hut B → USB.”

Hypothetical prepaid day using these rules (not live telemetry): Village Simulator.

Complementary to MPM / OpenAMI — not a substitute

ISV Phase 1 parks TC2.0 as the open HES for the installed SparkMeter base. MPM (MicroPowerManager) owns CRM + other prepaid families (STS tokens, OpenPAYGO SHS). Posting /api/v0/transaction/ from MPM into GroundBolt can share a wallet; running both as system of record without a split will double-count. Phase 2 OpenAMI MQTT / Street-EMS is a different track.

Glossary

SparkMAC — SparkMeter NAN protocol on the 2.4 GHz mesh (not Z-Wave).

AUTO — meter state: relay on iff HES credit (and plan) > 0.

HES — head-end system: utility software that commands and reads meters.

CIU — Customer Interface Unit: prepaid keypad / balance display at the home.

USB Gateway — hardware RF interface (laptop/site) to the meter mesh.

NAN — neighborhood area network: local 2.4 GHz mesh among meters (bridged by USB Gateway).

WAN — wide-area network: usually the site’s internet uplink to cloud.

LV — low voltage: customer / village distribution voltages.

Open Metering Infrastructure — A2EI CRM / operator platform layer; ThunderCloud and Nimbus both sit here.

SSE — Server-Sent Events: one-way live stream from server to client (readings / events).

OEM — original equipment manufacturer (e.g. another meter vendor).

SaaS — software-as-a-service (vendor-hosted cloud).

CRM — customer relationship management (accounts, tickets, portfolio ops).

SGC — Security Group Code (Nimbus universal key used for token generation).

TC1.x / TC2.0 — ThunderCloud software generations (field vs open foundation).
