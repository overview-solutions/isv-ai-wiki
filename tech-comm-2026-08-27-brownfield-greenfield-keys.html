Brownfield vs greenfield · OpenAMI key custody

ISV Technology Committee · 27 August 2026 · installed-base vs new OpenAMI sites · who holds prepaid keys

← Back to Meeting Notes · Home

Call capture

Core feedback: keep brownfield and greenfield work apart — do not mash installed SparkMeter / STS / ThunderCloud-OMS paths with new OpenAMI / Street-EMS sites in the same diagram, vendor row, or “standard” claim. Second: the new OpenAMI work has to answer who keeps the keys (prepaid token / STS trust), not only MQTT registers.

Open — do not fill from memory

Tech Comm did not name a key holder for OpenAMI on this call. Wiki tables below list candidate roles and what is already documented. Empty / unknown stays empty until a cited decision (OpenAMI text, STSA/KMC path, or operator ICD).

Separate the two tracks

Same village problems (revenue, theft, feeder loss) — different starting hardware and trust. Mixing them makes OpenAMI look like a drop-in for meters that already have an OEM KMC, and makes brownfield OMS look like it needs MeshEMS on day one.

Who keeps the keys? (OpenAMI — unanswered)

Prepaid without a named key holder is still OEM lock-in. northbound-mqtt-v0.1.json already puts STS key management on a separate STSA/KMC track — MQTT does not carry token keys. That split is correct; it does not say who runs the KMC when the site is greenfield OpenAMI.

Related facts already on the wiki (do not upgrade these to an OpenAMI key decision):

  • 25 Jun — STS provides key management for prepaid tokens; VMRS/MQTT exclude STSA operations; token path stays SMS/USSD/CIU.
  • 28 May — STS, OEM, and DLMS use different key hierarchies. Mixing stacks mixes keys.
  • 11 Aug — do not redo STS vending on the Open Code path; SparkMeter credit is GroundBolt wallet / CIU, not STS/OpenPAYGO.
  • Roadmap OpenAMI “could” — compose MPM / OpenPAYGO on VMRS + MQTT; not a new token scheme.

Wiki hygiene from this call

  • Label pages and diagrams brownfield or greenfield (or Phase 1 vs Phase 2) when both appear.
  • Vendor study / simulator / OMS notes stay brownfield unless the row is a new OpenAMI feeder.
  • OpenAMI page and MQTT profile stay greenfield telemetry + leakage; key custody is a tracked unknown, not a silent OEM default.

Follow-ups

  • Write a one-page OpenAMI key-custody options brief (operator vs OEM KMC vs OMS vs STSA) — decision, not a new crypto design.
  • Ask EnAccess / OpenAMI text: does the standard name a KMC role, or only MQTT/geo?
  • Keep brownfield STS/OMS work on Phase 1 pages; do not fold it into “OpenAMI standard” until keys are named.
