DLMS/COSEM

IEC 62056 · COSEM object model and DLMS messages on one page · meter and DCU

One meter, two jobs. COSEM is the shape of the data: which objects exist and what they are called. DLMS is the conversation that reads and writes those objects. OBIS codes are the names inside COSEM. A companion profile such as IDIS picks which of those objects a certified meter must carry.

COSEM

Companion Specification for Energy Metering. Interface classes and instances. Blue Book, IEC 62056-6-2, plus OBIS in IEC 62056-6-1. The model stays put when the wire changes.

DLMS

Device Language Message Specification. Application messages: associate, then GET, SET, or ACTION. Green Book, IEC 62056-5-3. The DCU is the client. The meter is the server.

Where a COSEM object sits

Indent is depth. Color is the job in the nest above. The physical device and the logical device are not COSEM objects. The physical device holds logical devices. The logical device holds a flat list of objects. Those objects are siblings. An object does not hold the devices above it, and it does not hold another object. A few objects hold a flat list of names, and those names point at siblings.

Physical device Not a COSEM object. The meter. It holds one or more logical devices. One management logical device is always there.
Logical device Not a COSEM object. Its service access point is an address. It holds the object list.

Three lists of names

Each box is one COSEM object. The table is the attribute that holds the list. Every row is another object that already sits in the logical device. The OBIS cell stays blue. A cell that names an object uses the object color. Green is only the reading, attribute 2. Purple, orange, and red replace that object color when the job is the session, another action, or the disconnect.

OBIS — six groups in the name

Interface classes a village read actually touches

1 · DataA named value with no scaler. Used for identifiers and flags when a Register is the wrong class.
3 · RegisterValue, scaler, unit. Import kWh, voltage, instantaneous power.
7 · Profile genericA buffer of captured objects. Load profiles live here. The village checklist leaves the full buffer out of the northbound payload.
8 · ClockMeter time. Readings without a clock are hard to audit.
15 · Association LNThe open session: who the client is, and which objects that client may see.
70 · Disconnect controlOutput state, plus methods to open and close the customer connection.

Class numbers are the public COSEM interface-class identifiers (IEC 62056-6-2). A manufacturer still chooses which instances to expose. That list is the vendor ICD, or an IDIS / Generic Companion Profile certificate when the meter has one. See where register work goes.

DLMS — the messages

SET writes an attribute. GET and SET also have with-list forms so one exchange carries several registers. A block transfer carries a long profile buffer. Event notification and data notification let the meter push without a fresh GET.

IDIS — how it shows up in the schema

Event tables in an IDIS package are values inside an existing event or alarm object, not a new OBIS group. Package history stays on the register checklist.

Where this sits on a village feeder

Score DLMS/COSEM on the meter and the DCU. The DCU is client toward the meter and server toward the head-end. Northbound of the gateway, the register checklist is a short JSON list of OBIS keys, not a second COSEM model. Site-to-cloud sync is a different hop.

STS is a different standard

Prepaid tokens are IEC 62055 (STS). A COSEM object can hold remaining credit and a disconnect method. The token cipher and the vending receipt are not DLMS messages. A keypad meter can vend with the uplink down. A DLMS read cannot.

A certified read is still a COSEM address inside a DLMS GET. The package catalog stays on the register checklist.
